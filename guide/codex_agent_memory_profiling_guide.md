# Codex 执行指导：本地小模型 Agent Memory Profiling 实验

> 目标：在本地服务器上构建一个最小可复现实验，用小模型支撑的 Agent 验证长期记忆规模增长时，`memory invocation / memory selection` 阶段是否产生可观的延迟、候选扫描、过滤、重排与上下文组织开销。
>
> 核心要求：实验必须可运行、可降级、可记录日志；不得因为代理、网络、Docker、Ollama 下载、pip 安装等问题无限等待或中途卡死。

---

## 0. 给 Codex 的执行原则

你是本地服务器上的实验执行助手。请严格遵守以下原则：

1. **先预检，再安装，再运行**。任何联网、拉镜像、安装依赖、下载模型之前，必须先运行网络和代理预检。
2. **所有可能卡住的命令必须加超时**。包括 `curl`、`pip`、`docker pull`、`ollama pull`、`python run_profile.py`。
3. **不得假设网络可用**。如果网络不可用，必须进入 offline-safe 模式，使用 hash embedding、mock LLM、numpy/local JSONL 检索继续完成实验。
4. **不得把实验绑定到单一组件**。优先使用 Ollama + Qdrant；如果不可用，必须自动降级到本地 mock LLM + numpy vector store。
5. **不得使用无限循环或后台不可控任务**。如果必须启动服务，必须记录 PID 或用 Docker compose，并提供停止命令。
6. **不得使用 sudo，除非用户显式允许**。如果 Docker 权限不足，只报告并切换到 numpy fallback。
7. **先运行最小 smoke test**。只有 smoke test 通过后，才允许扩大到 1k、5k、10k、50k、100k。
8. **每一步都写日志**。所有运行日志写入 `logs/`，实验结果写入 `results/`。
9. **最终必须输出一份实验状态报告**：说明使用了真实 Ollama/Qdrant，还是使用了 fallback；说明哪些阶段成功，哪些降级；给出 CSV 和图片路径。

## 1. 实验需要验证的命题

本实验不直接证明 PIM 有效，而是先验证以下 profiling 命题：

> 随着长期记忆规模、候选集合大小和 Agent 模块复杂度增加，Agent 的 memory invocation 阶段不再是可忽略的常数开销，而会表现出明显的 latency、candidate processing 和 context packaging 开销增长。

重点记录以下指标：

- `t_embed`：query embedding 时间；
- `t_search`：向量检索时间；
- `t_filter`：metadata filter 时间；
- `t_rerank`：rerank 时间；
- `t_pack`：memory context packaging 时间；
- `t_llm`：LLM 调用或 mock LLM 时间；
- `t_total`：端到端时间；
- `memory_invocation_ratio`：memory invocation 在端到端中的占比；
- `num_candidates`：候选数量；
- `num_after_filter`：过滤后数量；
- `prompt_chars`：最终 prompt 长度近似值；
- `backend_mode`：`qdrant` 或 `numpy_fallback`；
- `llm_mode`：`ollama` 或 `mock`；
- `embedding_mode`：`ollama_embedding` 或 `hash_embedding`。

## 4. 必须先创建的预检脚本：`scripts/preflight.sh`

请先创建并运行 `scripts/preflight.sh`。该脚本必须：

1. 检查 Python、pip、curl、docker、ollama 是否存在；
2. 检查直连网络是否可用；
3. 检查常见代理是否可用；
4. 生成 `.env.runtime`；
5. 不得因为网络失败退出整个实验；
6. 每个网络探测必须有 `--max-time` 或 `timeout`。

脚本内容建议如下：

```bash
#!/usr/bin/env bash
set -u
mkdir -p logs results data
LOG="logs/preflight.log"
: > "$LOG"

say() { echo "[$(date '+%F %T')] $*" | tee -a "$LOG"; }

say "== Basic command checks =="
for cmd in python3 pip curl docker ollama; do
  if command -v "$cmd" >/dev/null 2>&1; then
    say "FOUND $cmd: $(command -v "$cmd")"
  else
    say "MISSING $cmd"
  fi
done

say "== Python version =="
python3 --version 2>&1 | tee -a "$LOG" || true

DIRECT_OK=0
PROXY_OK=0
SELECTED_PROXY=""

say "== Direct network test =="
if timeout 8s curl -fsS --max-time 6 https://pypi.org/simple/ >/dev/null 2>&1; then
  DIRECT_OK=1
  say "Direct network OK"
else
  say "Direct network FAILED"
fi

say "== Proxy candidates test =="
PROXIES=(
  "http://127.0.0.1:21500"
  "http://127.0.0.1:7890"
  "http://127.0.0.1:7892"
  "http://localhost:21500"
  "http://localhost:7890"
  "http://localhost:7892"
)

for p in "${PROXIES[@]}"; do
  say "Testing proxy $p"
  if timeout 8s curl -fsS --max-time 6 --proxy "$p" https://pypi.org/simple/ >/dev/null 2>&1; then
    PROXY_OK=1
    SELECTED_PROXY="$p"
    say "Proxy OK: $p"
    break
  else
    say "Proxy failed: $p"
  fi
done

cat > .env.runtime <<EOF_ENV
# Generated by scripts/preflight.sh
DIRECT_OK=$DIRECT_OK
PROXY_OK=$PROXY_OK
SELECTED_PROXY=$SELECTED_PROXY
EXPERIMENT_OFFLINE_MODE=0
EOF_ENV

if [ "$DIRECT_OK" -eq 0 ] && [ "$PROXY_OK" -eq 0 ]; then
  say "No usable external network detected. Offline-safe mode will be used."
  sed -i 's/EXPERIMENT_OFFLINE_MODE=0/EXPERIMENT_OFFLINE_MODE=1/' .env.runtime
fi

if [ "$PROXY_OK" -eq 1 ]; then
  cat >> .env.runtime <<EOF_ENV
http_proxy=$SELECTED_PROXY
https_proxy=$SELECTED_PROXY
HTTP_PROXY=$SELECTED_PROXY
HTTPS_PROXY=$SELECTED_PROXY
PIP_DEFAULT_TIMEOUT=20
PIP_RETRIES=2
EOF_ENV
fi

say "== Docker check =="
if command -v docker >/dev/null 2>&1; then
  timeout 8s docker info >/dev/null 2>&1 && say "Docker usable" || say "Docker exists but not usable without permission or daemon not running"
fi

say "== Ollama check =="
if command -v ollama >/dev/null 2>&1; then
  timeout 8s ollama list 2>&1 | tee -a "$LOG" || say "Ollama exists but service/model list unavailable"
fi

say "Preflight finished. Runtime env written to .env.runtime"
exit 0
```

运行：

```bash
chmod +x scripts/preflight.sh
./scripts/preflight.sh
cat .env.runtime
```

如果 `.env.runtime` 中 `EXPERIMENT_OFFLINE_MODE=1`，后续不得强行 pip 下载、docker pull 或 ollama pull。

## 6. 代码实现要求

请实现以下 Python 模块。代码必须兼容 Python 3.8+，不能依赖 GPU，不能依赖 torch。

### 6.1 `src/timer.py`

实现一个简单计时器：

```python
import time
from contextlib import contextmanager

@contextmanager
def timer(stats: dict, key: str):
    start = time.perf_counter()
    try:
        yield
    finally:
        stats[key] = time.perf_counter() - start
```

### 6.2 `src/embedding_client.py`

必须提供两种 embedding：

1. `OllamaEmbeddingClient`：如果 Ollama embedding 模型可用则使用；请求必须有 timeout。
2. `HashEmbeddingClient`：永远可用的 fallback，不需要网络，不需要模型。

要求：

- 默认维度 384；
- hash embedding 必须 deterministic；
- 每次返回 `np.float32`；
- 结果需要 L2 normalize；
- 如果 Ollama 请求失败，自动退回 hash embedding。

### 6.3 `src/llm_client.py`

必须提供两种 LLM：

1. `OllamaLLMClient`：如果 `qwen3:4b` 或用户本地已有模型可用则使用；请求必须有 timeout。
2. `MockLLMClient`：永远可用，直接返回固定短文本，例如 `"mock answer"`。

要求：

- 不允许因为 Ollama 未启动而退出；
- 不允许无限等待；
- LLM mode 必须写入结果 CSV。

### 6.4 `src/synthetic_data.py`

生成长期运动健康助手记忆。每条记忆格式：

```json
{
  "memory_id": "m_000001",
  "user_id": "u_001",
  "content": "...",
  "memory_type": "health_constraint | episodic | feedback | profile | planning",
  "module_tags": ["planning", "reflection", "risk_control", "profile_update"],
  "entity_tags": ["knee", "sleep", "weight", "running", "diet", "fatigue"],
  "time": "2026-03-14",
  "importance": 0.87
}
```

生成规模：

```text
100, 1000, 5000, 10000, 50000, 100000
```

先用 100 做 smoke test。

### 6.5 `src/vector_store.py`

必须实现两个 backend：

1. `QdrantVectorStore`：如果 Qdrant 可用则使用；
2. `NumpyVectorStore`：永远可用 fallback，把 embedding matrix 存为 `.npy`，metadata 存为 `.jsonl`。

要求：

- 如果 Qdrant 连接失败，自动切换到 numpy；
- numpy search 使用矩阵乘法 `vectors @ query_vector`；
- 不要在 100k 数据上逐条 Python 循环计算相似度；
- backend mode 必须写入 CSV。

### 6.6 `src/memory_invocation.py`

实现完整 profiling pipeline：

```text
query
  -> query embedding
  -> vector search top candidate_k
  -> metadata filter by module and memory_type
  -> lightweight rerank
  -> package top_k memories into prompt context
  -> llm / mock llm
```

metadata filter 规则：

- planning：优先 `health_constraint`, `profile`, `planning`, `feedback`；
- reflection：优先 `feedback`, `episodic`, `planning`；
- risk_control：优先 `health_constraint`, `feedback`, `profile`；
- profile_update：优先 `profile`, `feedback`, `episodic`。

rerank 可以简单实现为：

```text
score = vector_score + 0.1 * importance + module_match_bonus + recency_bonus
```

记录所有阶段时间。

```bash
timeout 5s curl -fsS http://127.0.0.1:6333/collections >/dev/null && echo "Qdrant already running"
```


```bash

  -p 6333:6333 -p 6334:6334 \
  -v "$PWD/qdrant_storage:/qdrant/storage" \
```

- 只有网络可用时才 `docker pull qdrant/qdrant`；



## 12. 结果判断方法

Codex 在最终报告里请按以下逻辑解释结果：

如果出现以下任一现象，可以认为第一个动机点获得初步支撑：

- `memory_invocation_ratio` 在某些规模或任务下超过 10%；
- p95 memory invocation latency 随 memory size 增长明显上升；
- `candidate_k` 从 20 增加到 200 时，`t_filter + t_rerank + t_pack` 明显增加；
- planning、reflection、risk_control 的 memory invocation 明显高于 simple_semantic；
- 100k 规模下 memory invocation latency 比 1k 规模增加 3 倍以上。

如果没有出现上述现象，不要强行得出“瓶颈成立”。请如实报告：

> 当前设置下 memory invocation 还不是端到端瓶颈，但它对 memory size 和 candidate size 更敏感，后续应扩大 memory 规模、提高 metadata 复杂度、加入真实 reranker 或真实 Agent trace，再判断其是否成为长期运行瓶颈。
