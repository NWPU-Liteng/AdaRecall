# T3.4 noisy-or 证据选择

## 接口理解

- `run_proof_mainline.py` 的每个 demand 有固定 48 个候选，候选以
  `(demand_id, base_record_id)` 唯一标识；见证的 `retrieval_record_ids` 指向同一批
  source record 身份，而不是 Reader 提议时使用的 `rN` 短别名。
- `solve_witness_join()` 接收 demands、见证、relations 和全局 `evaluate(object_ids)`；
  `evaluate` 返回含 `feasible`、精确 `cost` 与物化内容的评估结果。v1 plan 包含
  `feasible`、`selected_witnesses`、`accepted_object_ids`、`cost`、`structure` 等字段。
- `_compatible()` 同时检查共享 binding 与 `same_binding` / `different_binding` /
  `source_relation`。noisy-or 允许多个同 demand 见证，因此每次加入候选时都要对全部
  已选见证逐对复用该函数。
- serving 的候选和见证均不读取 labels、golden answer、题型或标注证据。校准器只提供
  modality 的分段概率映射，且在加载时校验 T3.2 自哈希与配置哈希。

## 实现

- 新增 `scripts/omni_proof_join_noisy_or.py`。见证有效概率定义为
  `p_w = min(record calibrated probability)`；这是启发式定义，不代表事实充分性或
  QA 正确性。校准曲线按 T3.2 isotonic 断点做分段线性插值。
- 实现 SATURATE 式阈值二分和贪心选择：按 demand 计算 noisy-or 覆盖，最大化
  `F_t(S) = sum_d min(f_d(S), t)`；加入候选时同时要求预算可行、见证两两兼容，并遵守
  `max_witnesses_per_demand`。贪心比值为
  `gain / max(1, exact processor-token delta)`，平局按 `witness_id` 打破。
- 所有对象并集的 `evaluate` 结果在同一求解内缓存；`n_evaluate_calls` 因此等于实际
  唯一对象并集评估数。可选 `fill_redundancy` 在已选解基础上继续最大化
  `sum_d f_d(S)`，不会放宽精确可行性检查。
- `run_proof_mainline.py` 在 `join_algorithm=noisy_or_saturate` 时接入该求解器；无阈值
  成功或 query graph 无效时，按计划显式调用 v1 `select_retrieval_package()`。回退路径
  同时输出 `t_star`、`per_demand_coverage`、`witnesses_per_demand`、
  `n_evaluate_calls` 和 `join_fallback_used=true`，并保留失败求解结果供审计。
- `dfs_maxmin` 仍直接分派到原 `solve_witness_join()`；默认配置行为不变。
- 配置层要求 `noisy_or_saturate` 同时提供 calibrator path 与 sha256；未配置时 fail
  closed。已有 `noisy_or.levels=20`、`max_witnesses_per_demand=3`、
  `fill_redundancy=false` 默认值保持不变。

## 测试

- 定向测试：
  `pytest -q tests/test_omni_proof_join_noisy_or.py tests/test_extensions_config.py`
  ，结果 `13 passed`；连同候选策略、覆盖率、校准和标签隔离为 `30 passed`。
- 合成实例含 6 个见证、3 个 demand、binding 冲突、对象并集成本上限 5。暴力枚举的
  `max min f_d` 为 `0.7`（见证 `w0,w2,w5`）；求解器得到 `t*=0.7`、覆盖
  `d0=0.8,d1=0.7,d2=0.95`、成本 5、17 次唯一评估，比值 `1.0`，并验证可行、
  两两兼容、预算内和确定性。该比值只记录此合成实例，不外推一般最优性。
- 另覆盖 v1 `dfs_maxmin` 原函数分派、isotonic 插值、见证内概率取最小和配置必填项。
- 完整 CPU：`pytest -q tests -m "not gpu"`，结果 `801 passed, 3 failed`。三个失败仍是
  既有基线：缺少 `artifacts/hyperpim_sc_trace_v1`、旧 judge 状态字符串、重复 demand
  预期差异。

## 边界

- 单题仅有两个 accepted 见证，每个 demand 的有效概率相同，因此不能据此评估 noisy-or
  在多冗余见证下的收益，也不能报告延迟、token 或问答质量提升。
- 概率是 reranker 分数经 development 单题校准后的启发式值，不表示证据真实的语义
  充分性；本次结果不支持超出该定义的可靠性结论。
