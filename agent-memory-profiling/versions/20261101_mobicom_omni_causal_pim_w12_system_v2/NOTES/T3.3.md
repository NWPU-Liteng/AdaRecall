# T3.3 保形候选策略

## 实现

- 新增 `pim_backend/candidate_policy.py`，只读取 T3.2 calibrator 与 serving
  candidate records，不读取 labels、答案或题目标签。加载时同时校验归档内
  `sha256` 自哈希与配置中的 `calibrator_sha256`，并要求 calibrator 使用
  development split 和 48 候选宽度。
- `extensions.calibration.candidate_policy=conformal` 时，配置层要求
  `calibrator_path`、`calibrator_sha256` 均存在，且 `min_per_demand <= 48`。
  默认 `fixed48` 路径和参数保持不变。
- 每个 demand 按 `rerank_score` 降序、`query_rank`、`retrieval_rank`、
  `base_record_id` 确定性排序。先保留 `score >= tau_alpha` 的候选；数量少于
  `min_per_demand` 时按同一顺序补足，最终上限仍为 48。calibrator 中的
  `tau=null` 在 serving 解码为 `-inf`。
- 策略只筛选送入 frontier 与见证构造的候选；T3.1 candidate dump 仍保存完整
  48 候选池，便于独立评估候选池漏召回和保形覆盖率。
- `proof_plan.candidate_policy_stats` 输出每个 demand 的策略前后候选数、
  阈值保留数、补足数、缺失数，以及 compact candidate JSON 的 token 前后值。
  另记录最终一次见证构造的 Reader `structured_input_tokens`，并明确其包含
  prompt、demands、relations 与候选记录。
- 新增 `scripts/eval_conformal_coverage.py`，只接受 validation split dump。
  对每个有标注证据单元的 validation 题目计算
  `g_q`，并按 `g_q >= tau_alpha` 汇总经验覆盖率。`g_q=-inf` 表示候选池漏掉
  至少一个标注证据单元，即使 `tau_alpha=-inf` 也不计为覆盖。
- 修正 `run_proof_mainline.py` 中固定的访问元数据：现在根据实际 manifest
  split 输出 `validation_accessed` 与 `holdout_accessed`，development 运行仍
  保持 `false`。

## 测试

- 定向测试：
  `pytest -q tests/test_candidate_policy.py tests/test_eval_conformal_coverage.py tests/test_extensions_config.py tests/test_fit_calibration.py tests/test_label_isolation.py`
  ，结果 `24 passed`。
- 覆盖 calibrator 身份与自哈希、`null -> -inf`、阈值筛选、最少补足、48 上限、
  token 统计、conformal 配置必填项、validation-only 覆盖率报告，以及
  `g_q=-inf` 不计覆盖的规则。

  字符串、重复 demand 预期差异。

## GPU 验证：development

- 在 RTX 3090 GPU 0 上运行题目 `1_q_104`，服务耗时 `702.24 s`，未使用 GPU 2、4。
  输出为 `regression/golden_v2_t33_conformal/run/user_1_shard_0.json`，候选 dump
  为 `regression/golden_v2_t33_conformal/candidates/1/1_q_104.json`。
- 真实 T3.2 calibrator 在 alpha `0.1` 下的 `tau` 为 `-inf`，因此两个 demand 均为
  48/48 候选保留、补足数为 0。compact candidate tokens 为 14361 -> 14361，
  最终见证构造 Reader 输入为 8116 tokens。
- `tools/regression_check.py regression/golden_v2_t31_dump/run regression/golden_v2_t33_conformal/run`
  返回 `status=pass`、`failures=[]`、`nondeterministic_differences=[]`。

## GPU 验证：validation 覆盖率

- 在 GPU 0 上运行 validation 题目 `4_q_100`（user 4），服务耗时 `616.00 s`，
  run elapsed `641.59 s`，未使用 GPU 2、4。输出为
  `regression/golden_v2_t33_validation/run/user_4_shard_0.json`，且
  `validation_accessed=true`、`holdout_accessed=false`。
- 该题一个 demand，48/48 候选保留，compact candidate tokens 为 6724 -> 6724，
  最终见证构造 Reader 输入为 7178 tokens。
- validation 覆盖率报告位于
  `regression/golden_v2_t33_validation/conformal_coverage.json`。唯一题目的
  标注证据单元未进入 48 候选池，因此 `pool_miss_ratio=1.0`、`g_q=-inf`；
  alpha `{0.05,0.1,0.2}` 的 covered 均为 `0/1`，经验覆盖率均为 `0.0`，
  对应目标覆盖率分别为 `0.95/0.9/0.8`。

## 边界

- development 校准只有 1 题，三个阈值均为 `-inf`，因此本次策略没有实际缩小候选池；
  不能据此报告 token、延迟或部署收益。
- validation 覆盖率只有 `n=1` 且为候选池漏召回，不能估计总体覆盖率，也不支持任何
  超出 48 候选池的经验结论。
