# T2.2 接口理解

## Reader 解码路径

- `scripts/omni_proof_runtime.py::greedy()` 在每步先取最后一个位置的 logits，再在有 grammar 时
  通过 `xgrammar.fill_next_token_bitmask()` 填充 bitmask，并用
  `apply_token_bitmask_inplace()` 修改 scores，最后执行 argmax。
- `structured_call()` 使用 `contract_parse` 与 `witness_construct` 两类阶段；最终回答由
  `greedy()` 直接执行，对应 `answer` 阶段。
- Qwen3.5-4B 的 `tie_word_embeddings=true`，lm_head 与 embed_tokens 共享源权重。W12 dispatch
  已按 source weight identity 复用同一 bank layout，因此影子矩阵直接复用 lm_head 的 layout，
  不复制第二份量化公式。

## 影子模式边界

- `progressive_topk.lm_head=shadow` 要求启用 W12 bank route，且扩展的 `bits/group_size` 与
  W12 layout 一致；否则启动时 fail closed。
- 每个 worker 在主链启动时最多调用一次 `ProgressiveLmHeadShadow.__enter__()`，只构建一次
  lm_head `PlaneMajorMatrix`。lm_head 包装器上的 pre-hook 只保留最后位置 hidden 的 detached
  引用，不改变 forward 输出。
- 每第 `lm_head_shadow_every` 个 decode token 及 grammar forced token 进入校验；无 grammar 时
  使用全允许掩码，但 tokenizer 词表以外的 padding 行始终为 False。
- 只有影子计算，不替换 logits、argmax 或答案。progressive top-1 与 allowed 集合上的精确
  reference argmax 不一致时 raise；BF16/Reader 路径一致率只记录，不断言。
- singleton allowed 集合记为 `forced`，不调用 progressive 搜索，读取字节保持 0。

## 位平面导出与矩阵构建

- `W12BankLayout.export_codes_and_scales()` 从 bank storage 逐 bank/tile 解包，返回独立的
  `int16 [rows, cols]` 码值与 `float32 [rows, groups]` scales；修改导出数组不会影响 layout。
- 导出结果经 `from_codes()` 重排为全局 plane-major。码值 hash 仍按 little-endian int32
  分块计算，`_pack_planes()` 也按行分块，避免一次性创建整矩阵 int32/uint32 临时副本。
- torch 端口与 NumPy 端口使用同一套 NumPy 8-累加器 pairwise 求和顺序，保证 float64 得分和
  最终分数逐位一致。CPU 与 RTX 3090 上均验证了三种 plane schedule 的逐位一致性。

# T2.2 执行结果

## 实现

- 新增 `pim_backend/progressive_lm_head.py`：一次构建、lm_head pre-hook、bitmask 解包、
  forced 分支、三阶段统计与关闭态 summary。
- 扩展 `pim_backend/progressive_topk.py`：`TorchPlaneMajorMatrix`、`to_torch_matrix()`、
  `reference_scores()` 的 torch 分派、`progressive_topk_torch()` 与显式分块 reference 计算。
- 扩展 `pim_backend/w12_bank_layout.py`：只读 `export_codes_and_scales()`。
- 修改 `scripts/omni_proof_runtime.py` 与 `scripts/run_proof_mainline.py`，接入默认关闭的
  `progressive_lm_head_stats` 输出与三阶段调用参数。

## CPU 测试

- 定向测试：
  `pytest -q tests/test_progressive_topk.py tests/test_progressive_topk_torch.py tests/test_w12_bank_layout.py tests/test_w12_functional_dispatch.py tests/test_extensions_config.py`
  ，结果 `34 passed`。
- 新增测试覆盖：bank 导出逐位一致且非别名；NumPy/torch top-k 与 reference 得分逐位一致；
  row mask、多 schedule、多形状、整数行索引平局顺序；bitmask padding；forced 零读取；
  三阶段 summary。
- 完整 CPU：`pytest -q tests -m "not gpu"`，结果 `754 passed, 3 failed`。三个失败仍是既有
  基线：缺少 `artifacts/hyperpim_sc_trace_v1`、旧 judge 状态字符串、重复 demand 预期差异。

## GPU 验证

- 短 GPU 对照在 RTX 3090 上运行 300x1024、三种 schedule，NumPy 与 torch GPU 的 top-k 索引、
  分数和 stats 均逐位一致。
- golden 单题 `1_q_104`（user 1）开启 shadow 后完成，使用 GPU 0，未使用 GPU 2、4。
- lm_head 矩阵构建耗时 `38.78 s`；进程 host peak RSS `10,554,068,992 B`（约 9.83 GiB），
  CUDA peak allocated `13,410,835,968 B`（约 12.49 GiB）；plane 953,548,800 B，scale
  39,731,200 B。没有 OOM，也没有降采样。
- 影子统计：`checked_tokens=47`，`progressive_calls=47`，`forced_tokens=0`，所有 47 次
  `agree_bf16`、0 次 `disagree_bf16`，平均 `12` 轮；总读取 7,154,135,680 / 18,511,902,720 B，
  比例 `0.3865`。该题 grammar 未产生 singleton allowed 集，forced 分支由合成测试覆盖。
- 同题关闭态也用当前代码重跑至 `regression/golden_v2_t22_off`；其
  `progressive_lm_head_stats.enabled=false`，三阶段与总计的所有 token/字节计数均为 0。
- `tools/regression_check.py regression/golden_v2_t22_off regression/golden_v2_t22_shadow`
  返回 `status=pass`、`failures=[]`、`nondeterministic_differences=[]`。同题旧关闭态
  `regression/golden_v2_t15_off` 的 `answer`、`answer_token_ids`、`status`、
  `accepted_object_ids` 也与 shadow 行全部相等。
- 关闭态服务耗时 `701.38 s`，shadow 为 `731.45 s`；该差值仅用于说明 shadow 开销，
  不用于 PIM 性能结论。
- 结果目录：`regression/golden_v2_t22_shadow` 与 `regression/golden_v2_t22_off`。

## 边界

- 影子计算是 Host/PyTorch 参考路径，不声称实际 bank-PIM 时延或能耗。
- `weight_bytes_read/full` 来自渐进位平面访问计数；forced token 的读写字节均记为 0。
- shadow 开启会显著增加服务时间，因此输出明确标记 `performance_comparable=false`。
