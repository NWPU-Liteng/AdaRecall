# T2.4 接口理解

## 现有时序与容量模型

- `pim_backend/hyperpim_timeline.py::matrix_cycles(inputs, outputs, config)` 已按
  batch-1、输出行归属 bank 的方式计算权重读取、MAC、DRAM 行激活、scale、残差、
  外部传输和命令周期；`simulate_token()` 在其上累计多矩阵序列和 refresh stall。
- `HyperPimTimelineConfig` 已包含 `bank_count`、`row_bytes`、`tile_rows` 所需的 bank
  拓扑、内部带宽、MAC lane、`t_rcd/t_rp/t_rrd/t_faw` 和 refresh 参数，可作为 T2.4
  的 timing profile。
- `pim_backend/hyperpim_sc.py` 现有 `bank_resident_decoder_plan()`、
  `packed_bit_sliced_decoder_plan()`、`w8a16_mixed_precision_overhead()` 和
  `grammar_residency()`；T2.4 只新增布局/周期/能耗函数，不修改这些函数。

## 与计划描述的数据差异

- T2.1 的 `progressive_topk()` rounds 只输出 `rows_alive_before` 计数，没有保存每轮
  实际幸存行或 tile 身份。因此 `progressive_topk_cycles()` 无法从现有 stats 精确重建
  “幸存行涉及的 tile”。
- 本任务不修改 T2.1 的返回字段。新函数支持可选的行号/tile 身份输入；没有身份时，
  使用由 `rows_alive_before`、`bank_count` 和 `tile_rows` 推导的均匀 tile 计数上界，
  并在输出中显式标记 `tile_identity_source=count_bound_no_row_ids`，不把它表述为精确
  的幸存 tile 轨迹。
- T2.2 的 lm_head phase stats 只保留逐阶段 token 数、平均轮数和读取字节，没有逐 token
  rounds。`pim_replay.py` 对 lm_head phase 使用按阶段平均轮数与读取字节构造的代理轮次，
  并标记 `source=t22_phase_byte_proxy`；检索部分直接使用 T2.3 的真实 rounds。

## 新增接口

- `plane_major_layout_plan()` 输出 bank/tile 级 plane-major DRAM 行布局，以及同一
  `bits` 宽度 row-major 全量读取的行激活对照。
- `progressive_topk_cycles()` 逐轮计算 tile 行激活、内部读取、partial MAC、上下界更新、
  一次 host 阈值广播和 refresh，并调用现有 `matrix_cycles()` 生成同矩阵全量 GEMV 对照。
- `retrieval_gemv_workload()` 把检索打分表示为现有 timeline 可消费的矩阵 workload。
- `energy_model()` 只做计数到能耗的代数汇总；任何能耗参数缺失或为 `null` 时返回
  `params_missing`，不提供默认数值。

# T2.4 执行结果

## 实现

- `pim_backend/hyperpim_sc.py` 新增 `plane_major_layout_plan()`。它输出 bank 内
  tile、每 plane 的 DRAM 行数，以及同一位宽 row-major 全量读取的行激活对照。
- `pim_backend/hyperpim_timeline.py` 新增 `progressive_topk_cycles()`、
  `retrieval_gemv_workload()` 与 `energy_model()`；未修改任何现有函数的签名或返回结构。
- `progressive_topk_cycles()` 在 rounds 没有行身份时输出
  `tile_identity_source=count_bound_no_row_ids`；提供 `active_tile_ids` 时按实际 tile
  计算。显式 tile 路径已修正为读取对应 tile 的行数，而不是假设 tile 前缀。
- `scripts/pim_replay.py` 读取 T1.1 trace 与 shard 级 T2.2/T2.3 统计。T2.3 demand
  按 `question_id` 归属；T2.2 的 shard 级 lm_head 汇总只有在该 shard 恰有一个问题时
  才进入逐题回放，多题 shard 无法逐题归属时 fail closed。
- lm_head 阶段周期使用 `t22_phase_byte_proxy`：按 phase 的 progressive 调用次数、
  读取 plane 行数、平均轮数和 plane schedule 构造代理 rounds。`forced_tokens` 不进入
  该 phase 的 progressive 周期汇总。
- 回放分别累计四项估计的 counts 与 energy，避免把全精度基线和渐进替代路径重复相加。
- `configs/pim_profile_v2.yaml` 的 `host_round_trip_cycles` 与六项能耗参数均保持
  `null`/`TODO_CITE`；没有填入任何文献值或默认数值。

## CPU 测试

- 定向测试：
  `pytest -q tests/test_pim_v2_models.py tests/test_hyperpim_timeline.py tests/test_hyperpim_sc.py`
  ，结果 `32 passed`。
- 新测试覆盖：现有函数与冻结 v1 快照逐值一致；plane-major 与 row-major 行激活；
  显式稀疏 tile 身份；幸存行数越界；缺失 `host_round_trip_cycles` fail closed；
  能耗参数缺失、完整计算与未知参数；真实 shard 级统计契约及多题 lm_head 归属失败。
- 完整 CPU：
  `pytest -q tests -m "not gpu"`，结果 `774 passed, 3 failed`。三个失败仍是既有基线：
  缺少 `artifacts/hyperpim_sc_trace_v1`、旧 judge 状态字符串、重复 demand 预期差异。

## 真实数据回放

- 在 RTX 3090 GPU 0 上，用单题 `1_q_104`（user 1）生成
  `regression/golden_v2_t24_shadow_trace`；服务耗时 `732.95 s`，未使用 GPU 2、4。
- 该次运行同时开启 `workload_trace=on`、`progressive_topk.lm_head=shadow` 与
  `progressive_topk.retrieval=shadow`。trace 的检索矩阵为 `15490 x 1024`。
- T2.2 统计：`checked_tokens=47`、`progressive_calls=47`、`forced_tokens=0`，
  47 次 BF16 一致；平均 `12` 轮，读取 `7,154,135,680 / 18,511,902,720 B`，
  比例 `0.386461`。
- T2.3 统计：2 个 demand、共 24 轮，两个 `overlap@48` 均为 `1.0`，
  `shadow_assertions_passed=true`。
- `tools/regression_check.py regression/golden_v2_t23_shadow regression/golden_v2_t24_shadow_trace`
  返回 `status=pass`，答案、状态和证据选择无回归。
- 正式配置的 `host_round_trip_cycles` 仍为 `null`，直接运行
  `scripts/pim_replay.py <trace> <stats>` 按设计报错：
  `host_round_trip_cycles must be filled before replay`。

### 未校准代理回放

为验证真实数据的完整回放路径，另用仅限测试的 `host_round_trip_cycles=1000` 与默认
256-bank timing profile 生成
`regression/golden_v2_t24_shadow_trace/pim_replay_uncited_proxy_256bank.json`。
该值不是硬件参数、文献引用或可报告结果，只用于确认代码路径。四项周期如下：

| 阶段 | 全精度 GEMV | 仅语法掩码 | 语法掩码 + 渐进 | 检索 |
|---|---:|---:|---:|---:|
| contract_parse | 1,341,807,522 | 9,152,128 | 42,454,112 | - |
| witness_construct | 1,656,438,310 | 11,297,664 | 73,383,680 | - |
| answer_prefill | 9,253,794 | 0 | 0 | - |
| answer_decode | 351,645,964 | 2,463,104 | 38,220,064 | - |
| dense_retrieval | 65,590 | 0 | 356,544 | 356,544 |

- lm_head 渐进部分相对同矩阵全精度 GEMV 的 active-cycle 比例分别为
  `0.02304`、`0.03480`、`0.09440`。
- 在该未校准 host 值下，两个检索 demand 的 active cycle 分别约为全量 GEMV 的
  `4.99x`、`5.11x`；12 次 host 阈值往返和界更新占主导。不能据此声称检索渐进更快。
- 四个估计的 energy 均为 `params_missing`，缺失全部六项参数。

## 边界

- 当前 T2.1 rounds 没有幸存行身份；未提供 `active_tile_ids` 时所有 tile 命中都是显式
  标为 count bound 的上界代理。
- T2.2 只有 shard 级阶段汇总，无法恢复逐 token 的轮数和幸存行；单题 shard 可回放，
  多题 shard 被拒绝，而不是把 shard 总量复制给每一题。
- 所有周期都是解析目标模型输出，不是 RTL、硅片或物理 bank-PIM 测量；未声称端到端
  加速或能耗收益。
