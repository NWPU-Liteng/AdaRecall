# T1.1 接口理解

- `run_proof_mainline.py` 当前只在题级记录三个粗粒度 W12 阶段：
  `query_parser`、`source_grounding`、`reader_generation`。它们由
  `W12FunctionalDispatch.counter_snapshot()` 在阶段边界取快照，再通过
  `W12FunctionalDispatch.counter_delta(before, after)` 做差分；差分函数会校验 layout identity。
- 题目处理从 `request_started` 开始，依次经过 parser、query embedding、候选检索、
  reranker、frontier 编译、witness/grounding、join、最终 materialize 和 answer greedy。
  T1.1 的细粒度阶段在该流程内嵌套采集，不改动现有粗粒度字段及其计算方式。
- `omni_proof_runtime.greedy()` 已分别返回 `prefill_seconds` 与 `decode_seconds`，但现有
  prefill 计时从进入函数、GPU 输入搬运与 synchronize 之前开始，不能直接视为首次 forward
  时间。T1.1 会在首次 model forward 前后另做一次 synchronize 计时；原字段保持不变。
- `greedy()` 的语法约束路径为 `fill_next_token_bitmask(mask)`、按需
  `apply_token_bitmask_inplace()`、`accept_token()`。bitmask 是 xgrammar 的 32-bit word
  数组；`probe_grammar_sparsity.py` 已展示按小端位序统计 1 的数量并排除尾部填充位。
  T1.1 复用同一计数语义，在 `needs_mask=False` 时按全词表可用处理。
- Reader 的线性层调用次数可从 `W12FunctionalDispatch.modules` 的包装器读取：模块名来自
  `named_modules()`，形状为 `[out_features, in_features]`，调用次数由
  `bank_calls + prefill_fallback_calls + decode_fallback_calls` 组成。T1.1 在阶段边界取模块
  计数快照并做差分，不改变 dispatcher 的已有汇总字段。
- `stage_profiler: on` 只在题级输出新增 `stage_profile`；`workload_trace: on` 在
  `output.parent/trace/<user>/<qid>.json` 写题级 trace。两者任一开启时才创建 profiler，
  默认关闭时不增加计时、快照、bitmask 解包或输出字段。
- 计划列出的三个 Reader 阶段解释为 parser、witness/grounding 与 answer。前两者在各自阶段
  内记录 `prefill_wall_ms` 与 `decode_wall_ms`；answer 直接拆成 `answer_prefill` 和
  `answer_decode` 两个阶段，以满足九阶段清单。

# T1.1 执行结果

- 定向测试：`tests/test_stage_profiler.py tests/test_extensions_config.py
  tests/test_label_isolation.py tests/test_regression_check.py`，结果 `20 passed`。
- 完整 CPU 测试：`pytest -q tests -m "not gpu"`，结果 `700 passed, 3 failed`。三个失败与
  T0.3 记录一致，并已在 v1 逐项复现，属于既有基线问题，并非 T1.1 引入。
- 开关关闭回归：在当前代码上重新运行 golden 到 `regression/golden_v2_t11_off`；与
  `regression/golden_v1_run1` 比较为 `failures=[]`、
  `nondeterministic_differences=[]`。输出中没有 `stage_profile`，也没有 `trace/` 目录。
- 开关开启回归：`stage_profiler: on`、`workload_trace: on`，运行 golden 到
  `regression/golden_v2_t11_profile`。6 个题目均生成
  `trace/<user>/<qid>.json`，两个用户输出中的 6 行均含 `stage_profile`；逐题断言
  `stage_profile.stages`、`stage_wall_ms`、`coverage_fraction` 与 trace 完全一致。
- 阶段覆盖率：6 题最低为 `0.9944349571`（题 `1_q_104`），误差 `0.5565%`，满足 5% 验收阈值。
  `dense_retrieval.matrix_shape` 分别为 user 0 的 `[13861, 1024]` 与 user 1 的
  `[15490, 1024]`。Reader 线性层名称、形状和调用次数均从 W12 dispatcher 差值生成。
- `witness_construct` 是条件阶段：结构化题执行并记录该阶段；contextual 题按既有路径不调用
  witness Reader，因此 trace 中不伪造零耗时条目。该差异来自实际控制流，不属于缺失采集。
- GPU 使用：关闭与开启两组 golden 均只使用配置中的 GPU 0、1；未使用 GPU 2、4。
